## 1. 目的

系統目標（terry）：**讓操作有紀錄，讓各種使用者變輕鬆。**

這次改版要解決的事：

1. 學員只能用預先買好的堂數預約，沒有單堂（試上、單堂主題團課）的路。
2. 「已出席／未出席」只靠學員自己簽到，教練不能點名、不能更正，學員也不能申訴。
3. 取消與改期的規則不一致（改期不受期限限制；誰取消、為什麼沒有紀錄）。
4. 名詞混亂（套裝、待確認、已完成、未到場…），同一件事有多種說法。
5. 助教權限過大，可以動到和錢有關的事。

### 目標

- 每一筆預約在任何時間只有一個狀態；狀態、取消類別、付款狀態各自獨立、互不重疊。
- 任何會改變預約、堂數、付款的動作，都留下「誰、何時、做了什麼、為什麼」。
- 學員在選時段之前就知道自己能用什麼方式預約。
- 教練到場不會撲空；學員不會因為教練的失誤而損失堂數。

### 不做（non-goals）

- 線上金流。付款維持線下，系統只記錄申報與核對結果。
- Email 通知（既有決定：不做）。
- 平台管理員介入裁決異議（平台只看統計）。
- UI 視覺改版。本文件只定義流程、規則與資料；各畫面依 B2.1 另外出示意圖取得同意後才實作。

### 反目標（做成這樣就算失敗）

- 同一個概念在不同畫面出現不同名稱。
- 有任何一條路徑可以讓堂數或付款狀態改變卻沒有紀錄。
- 規則只做在畫面上，直接呼叫 RPC 可以繞過。

## 2. 名詞表（唯一用語）

畫面、通知、手冊、錯誤訊息一律使用「畫面用語」。程式碼與資料庫用「代碼」。

| 畫面用語 | 意思 | 取代的舊用語 |
|---|---|---|
| **單堂預約** | 不使用預購堂數，一次付一堂的預約（含試上） | — |
| **N 堂課**（例：10 堂課） | 教練上架的預購商品，N ≥ 2 | 套裝 |
| **剩餘堂數** | 學員手上還能用的堂數 | 套裝餘額 |
| **補堂** | 系統補發的 1 堂（見 §9.3） | — |
| **課堂管理** | 教練選單：管理可購買的 N 堂課、審核購買申請 | 套裝管理 |
| **購課紀錄** | 學員頁：上方剩餘堂數、下方單堂付款紀錄 | 我的方案 |
| **教練** | Owner 與助教的通稱。學員端永遠只出現「教練」 | — |
| **成班** | 團班（開班人數 ≥ 2）報名人數第一次達到開班人數 | — |
| **取消期限** | 開課時間往前 N 小時的那個時間點（N＝服務設定的取消期限時數） | — |

禁用詞：套裝、課卡、方案（指預購堂數時）、已完成、未到場。

## 3. 狀態定義

### 3.1 預約狀態（6 個，互斥）

| 畫面用語 | 代碼 | 意思 | 可轉往 |
|---|---|---|---|
| 待確認 | `pending` | 學員已送出，等教練確認 | 已確認、已取消 |
| 已確認 | `confirmed` | 預約成立，尚未上課 | 已出席、未出席、待點名、已取消 |
| 待點名 | `awaiting_attendance` | 課程已結束，沒有任何出席紀錄 | 已出席、未出席、已取消 |
| 已出席 | `completed` | 學員有來 | 未出席、已取消（僅改判，§8.4） |
| 未出席 | `no_show` | 學員沒來，不退回 | 已出席、已取消（僅改判，§8.4） |
| 已取消 | `cancelled` | 這堂課不上了 | 終態，不再變動 |

- 代碼 `completed`、`no_show` 沿用既有值，只改畫面用語。
- 「請假申請」「改期」「異議」「成班」都**不是**預約狀態。
- 團班的預約狀態與是否成班無關：已確認的預約可能尚未成班，畫面顯示「已確認・尚未成班（3/5）」。

### 3.2 取消類別（9 個，每筆取消恰好一個）

| 畫面用語 | 代碼 | 取消人 | 原因說明 | 堂數處理 |
|---|---|---|---|---|
| 學員取消 | `customer` | 學員 | 必填（常用原因或自填） | 退回 |
| 改期 | `rescheduled` | 學員／教練 | 學員自己改期免填；教練代改必填 | 轉到新預約 |
| 教練拒絕 | `coach_rejected` | 教練 | 必填 | 退回 |
| 逾期未確認 | `confirm_expired` | 系統 | 系統寫入 | 退回 |
| 請假 | `leave` | 教練 | 來源為學員申請時帶入申請原因；教練補登時必填 | 退回 |
| 教練取消 | `coach_cancelled` | 教練 | 必填 | **一律退回** |
| 學員臨時取消（教練代登） | `late_cancel` | 教練 | 必填 | **不退回** |
| 人數不足 | `under_min` | 系統 | 系統寫入 | 退回 |
| 舊資料（未分類） | `legacy` | — | — | — |

- 「請假」有三種來源（`leave_source`）：`request`（學員送出請假申請、教練同意）、`coach_entry`（教練點名或改判時補登）、`dispute`（異議成立）。來源為 `dispute` 且為逾期自動成立時，取消人身分記為系統。
- `late_cancel` 只能在「取消期限之後、開課之前」使用（§7.3）。
- `legacy` 只用於改版前的已取消資料，新資料不得使用。

### 3.3 堂數處理（3 種）

| 用堂數預約時 | 單堂預約時 | 代碼 |
|---|---|---|
| 退回 | 應退款（若已收款）／不需收款（若未收款） | `refunded` |
| 不退回 | 不退款 | `forfeited` |
| 轉到新預約 | 款項沿用 | `transferred` |

### 3.4 取消紀錄

每筆已取消的預約記錄 5 項：取消人（使用者＋身分：學員／Owner／助教／系統）、取消類別、原因說明、取消時間、堂數處理。前 4 項寫入後不可修改。

「堂數處理」欄位存的是**目前有效值**，只有異議成立時可由異議函式改寫（不退回 → 退回），原值與改寫原因寫入歷程（§10）。畫面顯示目前值，並可展開看原紀錄。

### 3.5 單堂付款

兩個獨立欄位：

- **付款方式**（學員預約時選）：`transfer` 我已轉帳／`onsite` 現場付款
- **付款狀態**：

| 畫面用語 | 代碼 | 進入條件 |
|---|---|---|
| 待收款 | `unpaid` | 預約建立時 |
| 已收款 | `paid` | Owner 標記（任何時間） |
| 應退款 | `refund_due` | 已收款的預約被取消且堂數處理為「退回」 |
| 已退款 | `refunded` | Owner 標記 |
| 不需收款 | `waived` | 待收款的預約被取消且堂數處理為「退回」 |

- 學員申報（我已轉帳）不等於已收款。教練確認預約是確認**時間**，不代表已收款。
- 「未出席」且「待收款」的單堂預約，在教練的學員資料上顯示「未收款 N 筆」。
- 服務可設定不接受現場付款（§5）。
- 學員可填付款備註（沿用既有 `receipt_note` 的做法）。
- 應收金額在預約建立時從服務的單堂價複製到預約上，之後服務改價不影響已成立的預約。

### 3.6 N 堂課的購買

- **購買申請**：審核中 `pending_review` → 已核准 `confirmed`／已拒絕 `rejected`／已撤回 `withdrawn`
  - 代碼沿用既有 `approval_status` 的值，新增 `withdrawn`。畫面一律稱「已核准」，不得出現「已確認」。
  - 同一學員、同一商品，同時只能有一筆審核中。
  - 學員申報付款沿用既有三種：我已轉帳／已部分付款／尚未付款。
- **已核准的購買**（由欄位推導，不另存）：可使用／已用完（剩餘 0，含已預約未上的）／已過期／已作廢
  - 已作廢：Owner 才能操作，必填原因。有未上課預約時不得作廢。

### 3.7 請假申請

審核中 `pending` → 同意改期 `approved_reschedule`／同意退回 `approved_refund`／不同意 `rejected`／已撤回 `withdrawn`／已失效 `void`

- 已失效：審核中時，預約因其他原因不再是「已確認」（教練取消、人數不足、學員已簽到）。
- 開課時仍是審核中 → 系統自動改為不同意（記錄為系統處理）。

### 3.8 異議

處理中 `open` → 成立 `upheld`／不成立 `dismissed`

### 3.9 時段（教練行事曆）

| 畫面用語 | 判斷方式 |
|---|---|
| 開放 | `status in (available, pending)` 且尚未開課 |
| 額滿 | `status = booked` 且尚未開課 |
| 關閉 | `status = cancelled` |
| 已結束 | 已過結束時間 |

資料庫的時段狀態值不變，只在畫面對應。時段不得顯示「待確認」這類預約用語。行事曆上時段內的每筆預約，用 §3.1 的用語標示，並附加標記：有請假申請、有異議、未收款。

## 4. 預約方式與確認規則

### 4.1 服務怎麼決定可以怎麼預約

| 條件 | 結果 |
|---|---|
| 服務「開放單堂預約」打開（單堂價必填且 > 0） | 可單堂預約 |
| 服務底下有上架中的 N 堂課，或學員對此服務有可使用的剩餘堂數 | 可用堂數預約 |
| 以上皆無 | 公開頁不顯示時段，只顯示教練聯絡方式；教練的服務設定頁顯示提醒「目前學員無法線上預約這個服務」 |

多堂不設開關：N 堂課的上下架就是唯一控制點。

### 4.2 預約成立時的狀態

| 預約方式 | 服務「一律需要教練確認」關閉（預設） | 打開 |
|---|---|---|
| 用堂數 | 已確認 | 待確認 |
| 單堂 | 待確認 | 待確認 |

既有行為「團班達開班人數時把所有待確認一起自動確認」**移除**（它會跳過教練對單堂預約的確認）。

### 4.3 預約時的檢查（全部在資料庫層）

1. 學員未被該教練封鎖。
2. 時段尚未開課、未額滿、未關閉。
3. 用堂數：該筆購買可使用，屬於同一服務，且**上課時間 ≤ 該筆購買的到期日**。
4. 單堂：服務開放單堂；付款方式為服務允許的方式。
5. 同一學員同一時段不得重複預約（既有限制）。

### 4.4 確認期限（只適用待確認）

- 確認期限 ＝ `max(取消期限, 預約建立時間 + 最短回應時間)`，但不得晚於開課時間。
- 到期仍待確認 → 系統取消（逾期未確認），退回，通知雙方。
- 到期前「提醒提前量」時提醒教練一次。
- 確認期限在預約建立時算好並存在預約上，之後不因設定變更而改變。

| 設定 | 說明 | 預設 |
|---|---|---|
| 開放單堂預約 | 打開時單堂價必填且 > 0 | 關（既有服務維持現狀＝只能用堂數） |

## 6. 團班與成班

適用於開班人數 ≥ 2 的服務。開班人數為 1 的服務不適用本節任何規則。

1. **成班判定**：時段的有效預約數（待確認＋已確認）第一次達到開班人數時，記錄成班時間。成班只判一次，之後不撤銷。
2. **成班後學員取消或改期離開**（在取消期限之前，僅限已確認的預約；人數算法與第 1 點相同＝待確認＋已確認）：
   - 取消後人數仍 ≥ 開班人數 → 可以自己取消，退回。
   - 取消後人數會 < 開班人數 → **不可自己取消**，只能送請假申請。畫面說明：「這堂課目前剛好達到開班人數，取消需要教練同意」。
   - 待確認的預約不受此限，可自由取消（教練尚未承諾）。
3. **未成班的自動取消**：到「開課時間 − 服務**當下**的取消期限時數」時仍未成班 → 系統取消該時段所有預約（人數不足），退回，時段關閉。這是時段層級的判定，不看個別預約上存的取消期限；個別預約的取消期限只決定該學員自己能不能取消。
4. 已成班的時段，之後不論人數如何變化（教練同意請假、教練取消個別學員），系統都不自動取消整堂。
5. **同一時刻的判定順序**：先判人數不足（整個時段），沒被取消的才判逾期未確認。
6. 排程頻率至少每 5 分鐘（PR #22 已改）。
7. 〔11/26 決議〕**成班通知**：成班當下通知這堂課的所有學員與該時段的教練「已成班，確定開課」。成班之後才報名的學員不另外通知，畫面直接顯示已成班。
8. 〔11/26 決議〕**團班時段的可見性**：有人預約但還沒額滿的時段，其他學員與未登入訪客必須看得到、進得了預約確認頁，公開頁顯示正確的已佔名額。名額數字由資料庫函式提供，不開放讀取他人的預約。（2026-11-26 查出現況做不到，列為第 2 階段第一個任務並可單獨上線。）

## 7. 取消與改期

時間分三段（取消期限記為 D，開課時間記為 S；「剛好等於 D」算在 D 之前）：

| 動作 | D 之前 | D 之後、S 之前 | S 之後 |
|---|---|---|---|
| 學員取消「待確認」 | 可，退回 | 可，退回 | — |
| 學員取消「已確認」 | 可，退回（受 §6.2 限制） | 不可，只能送請假申請 | 不可 |
| 學員改期「已確認」 | 可（受 §6.2 限制） | 不可，只能送請假申請 | 不可 |
| 學員改期「待確認」 | 不可（先取消再重新預約） | 不可 | — |
| 教練取消（退回） | 可 | 可 | 不可，只能點名 |
| 學員臨時取消・教練代登（不退回） | 不可 | 可 | 不可，只能點名 |

### 7.1 改期

- 只能改到**同一租戶、同一服務**的時段，不限負責成員（資料庫層檢查）。
- 待確認的預約不可改期，只能取消後重新預約（避免確認期限與付款紀錄在未確認時搬移）。
- 助教代改期或同意請假改期時，權限以**舊時段**是否為自己的時段為準；新時段可以是同租戶任何成員的時段。
- 用堂數時，新時段的上課時間必須 ≤ 該筆購買的到期日。
- 改期＝舊預約取消（類別：改期，堂數處理：轉到新預約）＋新預約。新預約記錄「由哪一筆改期而來」，歷程可以串接。
- 新預約的狀態：學員自己改期 → 依 §4.2；教練代改或同意請假改期 → 已確認。
- 〔11/26 決議〕**教練代改期**：開課前任何時間都可以，不受取消期限限制，也不受 §6.2 的團班人數限制（人數掉下去是教練自己的決定；已成班的時段不會因此被系統取消）。必填原因。教練要能**指定幫哪一位學員改**：入口在預約明細頁、預約管理清單，以及行事曆時段視窗的學員名單（入口細節以示意圖定案）。
- 單堂的付款紀錄（方式、狀態、金額、備註）複製到新預約。舊預約的付款欄位凍結不動；所有收款相關的查詢與統計一律排除堂數處理為「轉到新預約」的預約，避免同一筆款項被算兩次。

### 7.2 請假申請

- 可送出的條件：預約為已確認、尚未開課，且符合其一：已過取消期限；或被 §6.2 擋下。
- 學員必填原因，可附一個想改去的時段。
- 送出時通知教練；若送出時間早於「開課前提醒提前量」，到該時間再提醒一次。
- 送出畫面告知學員：「教練在開課前沒處理，就視為不同意。」
- 教練的處理：
  - **同意改期**：只能同意學員附上的時段，同意當下重新檢查名額。該時段已不可用，或學員沒附時段 → 不能選這項。
  - **同意退回**：預約取消（類別：請假，來源：學員申請），退回。
  - **不同意**：維持已確認。〔11/26 決議〕必填處理說明（同意改期、同意退回選填）。
- 同一筆預約被不同意後不可再送。學員可以在教練處理前撤回。〔11/26 決議〕撤回後可以再送（例如想換一個想改去的時段）。
- 〔11/26 決議〕教練看到待處理申請的地方：預約管理的篩選「請假申請」與卡片標記、儀表板的待辦區。不另開頁面。
- 有審核中的請假申請時，教練必須先處理申請才能點名。

### 7.3 教練主動取消

- **教練取消**：開課前任何時間，一律退回，必填原因。
- **學員臨時取消（教練代登）**：只在取消期限之後、開課之前，不退回，必填原因；通知學員，學員可提出異議。不退回的取消**繼續佔用那一個名額**：名額計算＝未取消的預約＋堂數處理為「不退回」的已取消預約。一對一因此維持額滿；團班的其他名額照常開放。異議成立改為退回後，名額仍不釋出。同一學員不可重新預約該時段。
- 關閉一個已有預約的時段＝對每筆預約做一次「教練取消」（同一個原因），不得靜默關閉。〔11/26 決議〕在行事曆的時段視窗新增「關閉時段」操作（Owner 或該時段的教練；開課後不可；已有學員簽到不可）。
- 〔11/26 決議〕「學員臨時取消（教練代登）」照排程在第 2 階段上線，但異議在第 4 階段才有。這段期間給學員的通知寫「如有疑問請聯絡教練」，第 4 階段再換成異議入口。空窗期登記錯誤，系統內沒有更正的方法（已知並接受）。

## 8. 點名

### 8.1 誰可以在什麼時候點

| 動作 | 時間 | 誰 |
|---|---|---|
| 學員自己簽到 → 已出席 | 開課前 30 分鐘到課程結束（既有） | 學員 |
| 教練點「已出席」 | 開課前 30 分鐘起 | 該時段的教練、Owner |
| 教練點「未出席」 | 開課後 | 該時段的教練、Owner |
| 教練補登「請假」（已取消，退回） | 開課後 | Owner |

### 8.2 待點名

- 課程結束時，已確認且沒有任何出席紀錄 → 待點名。
- 每天提醒該時段的教練與 Owner 一次。
- 進入待點名後滿「待點名期限」仍未點名 → 系統標為未出席（點名人記為系統），通知學員。

### 8.3 記錄

每個出席結果記錄：結果、來源（學員簽到／教練點名／系統）、操作人、時間。

### 8.4 改判

- 期限：從**目前這個出席結果產生的時間**起算「改判期限」內；有處理中的異議時，順延到異議結案。
- 已出席 ↔ 未出席：該時段的教練、Owner 可改，必填原因。
- 改為請假（已取消，退回）：Owner 才能，必填原因，操作前二次確認（已取消為終態，不可撤銷）。
- 對學員不利的改判（已出席 → 未出席）通知學員，學員可提出異議。

## 9. 堂數、到期與補堂

### 9.1 扣與退

- 用堂數預約成立時扣 1 堂；取消且堂數處理為「退回」時退 1 堂。已出席與未出席都不退。
- 每一次扣與退都寫入堂數異動明細（§10.2）。學員與教練在購課紀錄／學員資料上看得到明細。〔11/26 決議〕明細的畫面排在第 3 階段，跟購課紀錄頁改版一起做；第 2 階段只在現有清單上多顯示補堂。

### 9.2 到期

- 預約與改期時檢查：上課時間 ≤ 該筆購買的到期日（無到期日則不檢查）。

### 9.3 補堂

- 退回時，若原購買已過期或已作廢 → 不退回原購買，改發一筆「補堂」：1 堂，同一服務，到期日＝當下＋「補堂寬限天數」。
- 補堂在剩餘堂數區顯示為「補堂 1 堂・到期日」，並連回原因（哪一筆預約的退回）。
- 在新規則下，開課前的退回不會碰到已過期的購買；補堂主要發生在課後（教練補登請假、異議成立）與改版前建立的舊預約。

## 10. 紀錄（「每個動作都有紀錄」）

### 10.1 歷程

單一張歷程表，只增不改。每筆：租戶、對象種類、對象 id、相關預約 id（若有）、事件、操作人、操作人身分（學員／Owner／助教／系統）、原因、細節（JSON）、時間。

必須寫入歷程的事件：

| 對象 | 事件 |
|---|---|
| 預約 | 建立、確認、拒絕、取消（各類別）、改期（舊、新各一筆並互相連結）、簽到、點名、轉待點名、系統標未出席、改判、付款狀態變更（已收款、應退款、已退款、不需收款） |
| 請假申請 | 送出、提醒、同意改期、同意退回、不同意、系統自動不同意、撤回、失效 |
| 異議 | 提出、成立、不成立、逾期自動成立 |
| 購買 | 申請、核准、拒絕、撤回、作廢、補堂發放 |
| 服務 | 設定變更（前後值） |
| 時段 | 關閉、成班 |
| 成員 | 助教移除（含名下時段與預約的處理方式） |
| 學員 | 封鎖、解除封鎖 |

- 系統自動動作的操作人身分為「系統」，操作人為空。
- 預約明細頁顯示該預約的歷程（含相關的請假申請與異議事件），教練與學員都看得到。
- 通知是否送出沿用既有的 `notification_log`，不重複記錄。

### 10.3 站內通知〔11/26 決議新增〕

- 每一則通知不論有沒有推播出去（使用者沒開推播、關掉那一類、沒有訂閱裝置），都留下一筆站內紀錄：標題、內文、點了要去的站內頁面、時間、已讀時間。沿用 `notification_log`，加上標題、內文、連結三個欄位。
- 學員端：登入後的頁首有鈴鐺與未讀數字，點進去是通知清單；點一則會標為已讀並前往對應頁面；可全部標為已讀。
- 教練端現有的通知頁一起補齊：顯示標題與內文、可點進對應頁面；側欄的項目改名「通知」並顯示未讀數字。
- 站內一律留紀錄；推播偏好的開關只決定要不要推播到裝置。教練端推播偏好裡原本沒有作用的「站內」欄拿掉（資料表欄位保留、不再使用）。
- 「不推播、只留站內紀錄」的通知（例如既有待確認轉已確認）直接寫入站內紀錄。
- 通知只有本人讀得到；只有後端能新增；本人只能把自己的標為已讀。
- 〔11/26 決議〕**推播偏好整合成一份，而且要真的有作用**（以系統長期好用為主）：
  - **一個設定來源**：每個事件要不要推播，只存在勾選表那一份；學員端與教練端的設定頁用同一套表單、改同一份。原本只有學員端改得到、實際有作用的四個舊開關，值轉進勾選表後停用（欄位先保留）。原本教練端的勾選表與勿擾時段存得進去但沒有作用，修正時先以測試重現。
  - **一個發送入口**：所有通知經過同一個發送函式；要不要推播只在那裡判斷。
  - **事件種類只定義一次**：勾選表的列、發送時的類型、站內清單顯示的名稱共用同一份清單。
  - 推播偏好只決定「要不要推播到裝置」。所有通知一律留站內紀錄，包含被關掉推播的定時提醒（課前、每日、每週）。每日提醒與每週摘要只留最新一則未讀：新的一則寫入時，同類型舊的未讀自動標為已讀，避免關掉推播的人在站內無限累積。
  - **勿擾時段**內不推播、只留站內紀錄（不做延後發送）；時間以台北時間計。
  - 轉換時兩邊設定衝突：「關的優先」——任何一邊關過，轉換後就是關。上線時公告提醒教練：先前在推播偏好關掉的項目會開始生效。
- 〔11/26 決議〕**學員送出購買申請時通知教練**（原本沒有這則通知）。通知對象＝目前能核准購買申請的人：現在是租戶所有啟用中的成員；§12 的最終規則（只有 Owner）在第 3 階段收緊時，通知對象一起改。

### 10.2 堂數異動明細

每筆：購買 id、預約 id、增減（+1／−1）、原因代碼、操作人、時間。購買的已用堂數必須等於明細加總（以資料庫函式同一交易寫入保證）。

## 11. 異議

- 可提出的對象：預約被標為**未出席**；預約被**學員臨時取消（教練代登）**；被改判為未出席。
- 提出期限：從**該結果產生的時間**起算「異議提出期限」內（未出席用出席結果產生時間；學員臨時取消用取消時間）。不以通知送達時間計算，因為通知可能失敗。同一個結果（預約＋結果產生時間）只能提一次。
- 學員選擇主張並填說明：
  - 對未出席：「我有出席」或「我有事先請假」
  - 對學員臨時取消：「我沒有臨時取消」
- 處理人：Owner（助教不可處理）。通知 Owner 與該時段的教練。
- 處理結果：
  - 成立：未出席 → 依學員主張改為已出席，或改為請假（已取消，退回）；學員臨時取消 → 堂數處理改為退回（單堂為應退款／不需收款）。
  - 不成立：維持原結果，必填原因。
- Owner 在「異議處理期限」內沒處理 → 系統自動判成立，依學員主張執行，計入平台統計。
- 平台管理員只能看統計（各租戶異議數、成立數、逾期自動成立數），不介入裁決。

## 14. 做法選擇

### 14.1 規則放在哪一層

| 做法 | 說明 | 取捨 |
|---|---|---|
| **A. 資料庫函式（採用）** | 每個會改變預約、堂數、付款的動作都是一支 `security definer` 函式，內含權限、時間、狀態檢查，並在同一交易寫歷程與堂數明細 | 與現有架構一致（`book_with_purchase`、`cancel_booking` 等）；無法繞過；紀錄與資料變更一定同時成功或同時失敗。代價是 SQL 量大、要靠整合測試 |
| B. Server Action 內用 TypeScript 做規則 | 規則寫在 Next.js，資料庫只存資料 | 好寫好測，但學員可直接呼叫 REST 繞過；多步驟更新沒有交易保證。違反反目標 |
| C. 觸發器記錄歷程 | 用 trigger 自動寫歷程 | 省事，但 trigger 拿不到「原因」與「操作人身分」，系統動作也分不出來 |

採用 A。理由：反目標第 2、3 條只有 A 能滿足，而且現有程式已經是這個模式。

### 14.2 歷程表的形狀

採用單一歷程表（§10.1），不分成預約歷程、購買歷程多張表。理由：查詢「這位學員發生過什麼事」只需要一張表；事件種類之後會增加。堂數異動另立明細表，因為它要能加總核對。

### 14.3 既有函式的處理

`book_with_purchase`、`cancel_booking`、`reschedule_booking`、`confirm_booking`、`checkin_booking`、`auto_cancel_group_slot` 全部改寫或以新函式取代；舊函式在新函式上線後撤銷 `authenticated` 的執行權限，避免被直接呼叫繞過新規則。函式的切分與命名由實作者決定。

### 第 2 階段實作時對規格的補充（不改變規則，只是把沒寫到的情況講清楚）

- **名額的定義**（§7.3）：已佔名額＝未取消的預約＋取消類別為「學員臨時取消」的已取消預約。第 1 階段過渡期產生的「學員取消＋不退回」**不佔**名額。
- **成班與團班門檻用的人數**（§6.1、§6.2）：有效預約數＝待確認＋已確認，不含已出席、未出席、已取消。
- **§6.2 的適用對象**：只限制學員自己取消與自己改期；教練取消、教練代改期、教練同意請假不受限制。
- **補堂**（§9.3）：第 2 階段只處理「原購買已過期」；「已作廢」等第 5 階段有作廢功能後再接上。補堂被拿去預約、之後在補堂過期後退回，會再發一筆補堂。
- **請假申請的失效**（§3.7）：預約被取消（教練取消、關閉時段、人數不足）、被改期、學員已簽到時，審核中的申請一律變成已失效。
- **同意請假改期**（§7.2）：新時段的名額、到期日、是否仍可預約，在教練同意當下重新檢查；任何一項不過，整筆不變、申請維持審核中。
- **已過上課時間卻仍待確認的舊預約**：以人數不足（系統）取消並退回堂數（查到 1 筆），寫在資料轉換檔的第二段。
